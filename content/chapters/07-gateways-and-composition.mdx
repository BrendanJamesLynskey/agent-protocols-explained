<Layer kind="concept">

A host with ten MCP servers holds ten connections, ten sets of credentials and ten tool lists. A **gateway** collapses them into one: it is an MCP server to the host and an MCP client to each server behind it. It lists their tools, merges them, and routes each `tools/call` to the server that owns the tool. Step through the animation: one `tools/list` from the host fans out to the <V of="gateway.flat.tools" fmt="int" /> tools of four servers, and comes back as one list.

**Names collide.** Tool names are only unique within a server. Here `files`, `github` and `web` all offer `search`, and `files` and `github` both offer `read_file`. The spec's [tools page](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) (accessed 2026-10-08) says it plainly: aggregators "MAY encounter naming collisions" and "SHOULD implement a disambiguation strategy such as prefixing tool names with a server identifier", and the server's own `serverInfo.name` "SHOULD NOT be relied upon" for it, since it need not be unique.

- **flat**: the first server registered wins each name. The host sees <V of="gateway.flat.merged_tools" fmt="int" /> tools; three are shadowed, silently. When the model asks for `search` meaning the web, the gateway sends it to <V of="gateway.flat.routed_to" fmt="raw" />, and the model gets "no matches in the project" back: a wrong answer, not an error.
- **prefix**: every tool is exposed as `alias.tool` with an alias the gateway chooses (the MCP series writes `github__search`; any separator among the characters the spec allows for tool names, letters, digits, `_`, `-` and `.`, will do). All <V of="gateway.prefix.merged_tools" fmt="int" /> are reachable and `web.search` goes to <V of="gateway.prefix.routed_to" fmt="raw" />.
- **filtered**: prefixed, and only an allow-list for the task is exposed: <V of="gateway.filtered.merged_tools" fmt="int" /> tools.

**The tokens are the bill.** The model reads every exposed definition in its prompt on every turn. The four servers' lists cost <V of="gateway.flat.direct_tokens" fmt="int" /> tokens together (Qwen2.5 tokenizer); prefixing every name costs a little more (<V of="gateway.prefix.merged_tokens" fmt="int" />), while flat shadowing "saves" tokens only by losing tools (<V of="gateway.flat.merged_tokens" fmt="int" />). Filtering to what the task needs cuts the list to <V of="gateway.filtered.merged_tokens" fmt="int" />. The same cost seen from the harness's side, and what it does to the context window, is [Agent Harnesses Explained, the context budget](https://agent-harnesses-explained.vercel.app/learn/03-the-context-budget).

**What else a gateway does.** It is also where a deployment puts authentication to the servers, audit logs and policy: the [OAuth_for_MCP](https://brendanjameslynskey.github.io/OAuth_for_MCP/#/12) deck walks through a real one (Docker's MCP Gateway), and the two playgrounds below run an aggregating gateway and a per-server bridge in Docker Compose.

</Layer>

## Caching the lists, and keeping them in order

A gateway answers the same `tools/list` for many hosts, so it is the natural place to cache it. The 2026-07-28 revision makes that explicit with a **`CacheableResult`**: `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` and `server/discover` must now carry two hints ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching), accessed 2026-10-16):

- **`ttlMs`**, how long the result may be considered fresh, "analogous to HTTP `Cache-Control: max-age`". It is a freshness hint, not a promise, and not a polling interval; `0` means immediately stale. It complements the `listChanged` notifications rather than replacing them.
- **`cacheScope`**, `"public"` or `"private"`. A public result has no user-specific data, and "any client, shared gateway, or caching proxy" may serve it to any user. A private one may be reused only for the same authorisation context: caches "MUST NOT be shared across authorization contexts". A gateway that filters tools by the caller's scopes ([chapter 6](/learn/06-authorisation)) is serving private lists, whatever its servers said.

The same revision adds a **SHOULD** that matters to the model as much as to the gateway: servers should return `tools/list` in a deterministic order, the same order whenever the set of tools has not changed, because that "enables clients to reliably cache the tool list and improves LLM prompt cache hit rates when tools are included in model context" ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). That is the "tools reordered every turn" layout of [Agent Harnesses Explained, prompt caching](https://agent-harnesses-explained.vercel.app/learn/04-prompt-caching), where rotating the tools every turn throws away the cached prefix after the system text, prevented at the source. A gateway keeps the promise only if its own merge is deterministic too: this engine merges in server-registration order, so the same four servers always give the same list.

The four servers, their tools and descriptions are invented for the example; the messages follow the 2026-07-28 revision (the `_meta` envelope, `resultType`). Token counts are Qwen2.5's over the definitions as a chat template writes them; other models' tokenizers give other numbers, and a real host may add its own wrapper text. The gateway's policies are this engine's, not any product's.

<Layer kind="maths">

With $S$ servers each exposing $k_s$ tools of about $d$ tokens each, the list costs $T_{\text{list}} \approx d \sum_s k_s$ tokens on **every** model call, so over a session of $n$ calls the tool list alone costs $n\,T_{\text{list}}$ input tokens (before any prompt caching). Prefixing changes $T_{\text{list}}$ only by the extra name tokens; filtering changes it by the fraction kept, here <V of="gateway.filtered.merged_tools" fmt="int" /> of <V of="gateway.flat.tools" fmt="int" /> tools.

Shadowing is a probability problem for the model as well as a routing one: if the model picks among same-named tools by name alone, a flat merge maps all of them to one server, so the call is right only when the model meant the first-registered server.

</Layer>

**In production.** A server written with the official MCP Python SDK (2.3.0) sets the cache hints per method; the tool's schema is generated from the function's signature and docstring:

```python
from mcp.server import MCPServer
from mcp.server.caching import CacheHint

mcp = MCPServer(
    "notes",
    version="1.0.0",
    # 2026-07-28: the tool list is the same for every user, so gateways may share it for a minute
    cache_hints={"tools/list": CacheHint(ttl_ms=60_000, scope="public")},
)


@mcp.tool()
def search_notes(query: str, limit: int = 5) -> list[str]:
    """Search the team's notes; return the titles of the best matches."""
    notes = ["Cache layout", "Retry budget", "Sandbox rules"]
    return [n for n in notes if query.lower() in n.lower()][:limit]


if __name__ == "__main__":
    mcp.run()  # stdio
```

Run here over stdio with the SDK's own client in 2026-07-28 mode, its `tools/list` result carried `"ttlMs": 60000, "cacheScope": "public", "resultType": "complete"`; without `cache_hints` the SDK sends the safe defaults, `0` and `"private"`.
