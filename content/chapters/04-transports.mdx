<TransportWidget>
  <Eq
    label="A message takes the one-way latency plus its bytes, payload and framing, divided by the link rate; the overhead share is framing bytes over all bytes"
    tex="\begin{gathered} t = \htmlClass{hl-lat}{\ell} + \frac{8\,(\htmlClass{hl-payload}{b_p} + \htmlClass{hl-framing}{b_f})}{\htmlClass{hl-rate}{R}} \\ \phi = \frac{\sum \htmlClass{hl-framing}{b_f}}{\sum (\htmlClass{hl-payload}{b_p} + \htmlClass{hl-framing}{b_f})} \end{gathered}"
  />
</TransportWidget>

<Layer kind="concept">

The messages of [chapter 2](/learn/02-json-rpc-and-the-life-cycle) need a way to travel. The specification defines two.

<span id="pr-stdio" />

**stdio.** The host starts the server as a child process and writes JSON-RPC messages to its standard input, one per line; the server answers on its standard output. "Messages are delimited by newlines, and MUST NOT contain embedded newlines", and the server may log to standard error ([stdio, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), accessed 2026-10-08). The framing is one byte per message. Nothing crosses a network, so there is nothing to authorise: the server runs as the user.

**Streamable HTTP.** The server is a web service with one endpoint. Every client message is its own HTTP POST; the server answers a request with one JSON body, or with a Server-Sent Events (SSE) stream that carries notifications (such as progress) before the result ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), accessed 2026-10-08). In 2025-11-25 the server could also send its own requests on that stream, `initialize` minted a session ID that every later request carried, and client notifications got `202 Accepted`. In 2026-07-28 there are no sessions; instead each POST repeats the method and the tool, resource or prompt name in `Mcp-Method` and `Mcp-Name` headers, so a load balancer or gateway can route without reading the body, and the server must reject a request whose headers and body disagree.

<span id="pr-framing" />

Pick a session and switch transports. The JSON is the same; the framing is not. On stdio the short session costs <V of="transports.legacy_tour.stdio.overhead" fmt="bytes" /> of framing; on Streamable HTTP <V of="transports.legacy_tour.http.overhead" fmt="bytes" />, <V of="transports.legacy_tour.http_overhead_frac" fmt="pct" /> of everything sent, in <V of="transports.legacy_tour.http.posts" fmt="int" /> POSTs. The same session in 2026-07-28 sends fewer messages (no handshake, no ping), so its HTTP framing is <V of="transports.modern_tour.http.overhead" fmt="bytes" />, <V of="transports.modern_tour.http_overhead_frac" fmt="pct" />. A session with progress turns its tool call's response into an SSE stream: one header, then one `event: message` per notification.

</Layer>

## When the stream breaks

<DropWidget>
  <Eq
    label="Resumed, the call finishes when both the work and the reconnect are done; sent again, the reconnect and all the work come after the break, and the k steps done before it are wasted"
    tex="\begin{gathered} T_{2025} \approx \max\!\big(\htmlClass{hl-work}{n\,s},\; t_{\text{break}} + \htmlClass{hl-reconnect}{t_r}\big) \\ T_{2026} \approx t_{\text{break}} + \htmlClass{hl-reconnect}{t_r} + \htmlClass{hl-work}{n\,s} \\ W = \htmlClass{hl-redone}{k}\,s \end{gathered}"
  />
</DropWidget>

<Layer kind="concept">

A long tool call reports progress over an SSE stream, and the connection drops after $k$ of its $n$ events. The two revisions disagree about what happens next.

**2025-11-25: resume.** Disconnection "SHOULD NOT be interpreted as the client cancelling its request", and the server "MAY make the stream resumable" by giving each SSE event an ID ([transports, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), accessed 2026-10-08). The animation shows a server that does: it keeps working and keeps the events; the client reconnects with an HTTP GET carrying `Last-Event-ID` and the session ID, and the server replays what it missed. With $n = 5$ and a break after event 2, the call finishes at <V of="transports.drop.handshake-5-2.elapsed_ms" fmt="ms" /> and no work is repeated.

<span id="pr-send-again" />

**2026-07-28: send again.** Resumption is gone: "A broken response stream loses the in-flight request; clients MUST re-issue it as a new request with a new request ID", and closing the stream is itself the cancellation signal ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), accessed 2026-10-08). The server stops; the client sends the call again and the work starts over. The same break now costs <V of="transports.drop.modern-5-2.redone_steps" fmt="int" /> repeated steps and the call finishes at <V of="transports.drop.modern-5-2.elapsed_ms" fmt="ms" />. In exchange the server keeps no buffers and no sessions, so any instance can serve any request: the revision traded a rare slow path for simpler servers. For long-running work the same revision moved tasks into an official extension (`io.modelcontextprotocol/tasks`), which the client polls with `tasks/get`.

</Layer>

<Callout kind="illustrative">

Latencies are **illustrative parameters**, not measurements: a 0.05 ms pipe and a 150 ms process start for stdio; 20 ms one way, 50 Mbit/s and 80 ms to connect for HTTP; 200 ms per progress step and 1 s for the client to notice a break and reconnect. The HTTP header sets are the minimal ones the specification requires plus `Host` and `Content-Length` (real stacks add more); byte counts are exact for these messages and headers. The resuming server is one that chose to support resumption, which 2025-11-25 allowed but did not require.

</Callout>

<Layer kind="maths">

A message of $b_p$ payload bytes with $b_f$ bytes of framing, on a link of one-way latency $\ell$ and rate $R$ (bits per second), arrives after $t = \ell + 8(b_p + b_f)/R$. On stdio $b_f = 1$ and $\ell$ is tiny, so the cost is the server's start-up; on HTTP $b_f$ is a request line and headers, or an SSE event prefix: <V of="transports.legacy_tour.http_overhead_per_message" fmt="num" /> bytes per message on average in the short session, comparable to a small message itself, which is why the overhead share $\phi$ is large for chatty sessions and small for big results.

For the broken stream, with $n$ steps of $s$ seconds of work, a break at $t_{\text{break}}$ after $k$ events and a reconnect time $t_r$: resuming finishes at about $\max(n s,\; t_{\text{break}} + t_r)$, because the server never stopped; re-sending finishes at about $t_{\text{break}} + t_r + n s$ and wastes $W = k s$ of work. The difference grows with how late the break comes.

</Layer>

- stdio: the server is a child process, one JSON message per line, nothing to authorise.
